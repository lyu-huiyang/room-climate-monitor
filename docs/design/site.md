# room-climate-monitor 项目网站 — 设计文档

- 日期：2026-11-10
- 范围：GitHub Pages 上的项目网站，包括落地页和用模拟数据运行的在线 demo

## 1. 背景与目标

现在想了解这个项目的人只能看 README：四张截图和一段 `docker compose` 命令。决定要不要在自己的服务器上部署之前，他们想先亲手用一用。

项目网站给这些人一个不用安装任何东西的入口：打开链接，就能用上和真实部署完全一样的网页，看到多个房间的实时读数和历史曲线；用完觉得合适，照着页面上的三步去部署。

**访客：** 从 README 点进来的人。他们看完网站要能回答两个问题："我家能不能用"和"部署麻不麻烦"。

**成功标准：**

1. 打开网站首屏就能看到并操作一个正在运行的 demo：多个房间同时在线，读数在页面开着时每分钟更新一次，能进入房间翻看历史曲线。
2. demo 就是 `web/` 里的那套网页本身，不另做仿制品；以后改了网页，demo 自动跟着变。
3. 落地页一页讲清楚：它是什么、需要什么硬件、怎么部署。
4. 推送到 `main` 且检查通过后，网站自动发布。

## 2. 已定决策

| 项 | 决策 |
|---|---|
| 托管 | GitHub Pages，地址 `https://lyu-huiyang.github.io/room-climate-monitor/`，不绑自定义域名 |
| 发布方式 | GitHub Actions 构建并发布（Pages 来源选 "GitHub Actions"），**不建 `gh-pages` 分支**，仓库仍然只有 `main` 一个分支 |
| 何时发布 | 推送到 `main`，并且和 CI 一样的检查通过之后；检查不过就不发布 |
| 页面布局 | 落地页首屏左边是介绍，右边嵌一部手机外框，里面是可以直接操作的 demo；见第 4 节 |
| demo 的实现 | 构建一个"演示模式"的 `web/` 网页：页面、组件、hooks 都不改，只把对后端 `/api/...` 的请求换成浏览器里生成的模拟数据 |
| 后端 | 没有后端，网站全部是静态文件 |
| 工程位置 | 落地页和 demo 都放在现有的 `web/` 工程里，作为额外的页面入口，共用一套工具链、依赖和锁文件 |
| 版本固定 | 和仓库其他部分一样，所有新增依赖和 Actions 都写到具体版本；包管理用 pnpm |
| 语言 | 落地页中英双语，和网页一样默认跟随浏览器语言，可以手动切换 |
| 模拟数据 | 在浏览器里按当前时间生成，不使用任何真实读数 |

## 3. 不做的事

- 博客、文档站、多页面网站：只有一个落地页加 demo。
- 自定义域名、访问统计、第三方脚本。
- 在 demo 里注册房间、修改设置：真实网页本来就是只读的，demo 也一样。
- 和真实服务端相关的任何东西：网站不连接、不代理任何服务端。

**会被视为失败的情况**（即使网站能打开）：

- demo 和真实网页长得不一样或者行为不一样，例如为了 demo 改了组件、另写了一套页面。
- 访客的浏览器里留下一个"可安装的应用"或离线缓存：demo 不能注册 PWA 的 service worker，也不能出现"安装到桌面"提示。
- 模拟数据里出现真实的家庭信息：只用通用房间名，不用真实读数。
- 为了发布网站多出一个长期分支。

## 4. 落地页

一页，从上到下：

### 4.1 首屏

- **左边**：
  - 一句话说清楚它是什么，例如"家里每个房间的温度和湿度，一眼看全" / "Temperature and humidity of every room at home, at a glance"。
  - 一行小字："ESP32 + 传感器 · 自托管 · 一个容器 · 开源 MIT"。
  - 两个按钮："部署指南"（跳到本页 4.3 节）和 "GitHub"（仓库地址）。
- **右边**：一部手机外框，里面是正在运行的 demo，可以直接点进房间、切换时间范围。手机框下方一个"全屏打开 demo"的链接。
- **窄屏（手机访问）**：不显示手机外框（在手机里再套一部手机没有意义），首屏改成介绍加一个醒目的"打开 demo"按钮，进入全屏 demo。
- demo 区域要标明"演示数据"，避免访客以为看到的是作者家的真实读数。

### 4.2 硬件

- 一块 ESP32-C3 SuperMini、一个 SHT40、一个 AHT20，接线和烧录指向 [firmware/README.md](../../firmware/README.md)。
- 价格：只有在维护者提供了具体数字时才写；没有就不写价格。

### 4.3 部署三步

每步列出能跑通的最少几行命令加一句说明，命令和 README 的快速开始保持一致（例如数据目录的 `chown` 不能省，烧录前要先复制并填写配置文件）：

1. 用 Docker Compose 启动服务端。
2. 用 `rcm room add` 注册房间，拿到设备密钥。
3. 把配置写进固件并烧录。

每一步链接到 README 或固件 README 对应的详细说明。

### 4.4 为什么自托管

几句话：数据不出家门，没有云服务、没有账号，一个 SQLite 文件就是全部数据。

### 4.5 页脚

GitHub 链接、MIT 许可证、语言切换。

## 5. demo

### 5.1 和真实网页的关系

- demo 用的就是 `web/src` 里的 `App`、页面、组件和 hooks，界面和交互与真实部署完全一致，包括深色模式和中英文切换。
- 只有两处不同：
  1. 对 `/api/...` 的请求由浏览器里的模拟数据回答，不发网络请求。
  2. 不注册 PWA 的 service worker，不提供安装。
- demo 的地址在网站的一个子路径下（例如 `/room-climate-monitor/demo/`）。进入房间后刷新页面、或直接打开某个房间的链接，都要能正常显示，不能出现 GitHub Pages 的 404 页面。
- 全屏 demo 页面顶部有一条小横幅："演示模式 · 数据为模拟"，并链接回落地页。手机框里嵌的 demo 也要能看出是演示数据（可以由落地页在框外标注）。

### 5.2 模拟的房间

四个房间，三个在线、一个离线：

| ID | 中文名 | 英文名 | 状态 |
|---|---|---|---|
| `living-room` | 客厅 | Living room | 在线 |
| `bedroom` | 卧室 | Bedroom | 在线 |
| `study` | 书房 | Study | 在线 |
| `balcony` | 阳台 | Balcony | 离线：最后一条读数在几个小时之前 |

- 房间名跟随网页当前的语言显示（真实部署里房间名是用户自己起的，demo 里按语言给出对应的名字，免得英文访客看到中文名）。网页默认一分钟才重新请求一次，所以切换语言时 demo 要让房间数据立即刷新；落地页和手机框里的 demo 语言保持一致。
- 舒适区间用服务端的默认值（温度 22–26 °C，湿度 40–60 %）；可以让某个房间的读数在一天里有一段时间超出区间，让访客看到舒适区间的提示效果。

### 5.3 模拟数据怎么生成

- 沿用 `server/scripts/seed_demo.py` 的思路：温湿度围绕各房间的基准值做以一天为周期的起伏，两个传感器（`sht40`、`aht20`）之间有一点固定的差值，信号强度在一个范围内变化。
- 数据由时间决定：同一个时间点，不管什么时候生成、刷新多少次，都得到同样的读数。这样刷新页面后曲线是连贯的，不会每次都变样。
- 读数对齐到整分钟。`latest` 是当前这一分钟的读数，`age_s` 按当前时间计算。页面开着时，网页本来就每分钟重新请求一次房间数据，所以读数每分钟跳一次。
- 历史覆盖网页支持的全部时间范围（`8h`、`24h`、`7d`），点和桶宽与服务端接口一致（见 [server-web.md](server-web.md) 第 4.3 节）。离线房间的历史在最后一条读数之后断开。
- 返回的数据结构必须和 `web/openapi.json` 描述的接口一致；类型检查要能发现不一致。
- 不存在的房间返回 404，网页显示的效果和真实部署一样。

## 6. 构建与发布

- `web/` 增加一个网站构建：输出落地页和演示模式的 demo，资源路径按 `/room-climate-monitor/` 子路径处理。现有的构建（Docker 镜像里用的那个）保持不变，不受影响。
- 新的 GitHub Actions 工作流：在推送到 `main`、并且 CI 的全部任务（`check` 和 `docker`）都通过后，构建网站并发布到 GitHub Pages。用官方的 Pages Actions，版本写死；权限只给发布需要的那几项。
- 维护者需要手动做一次：Settings → Pages → Source 选 "GitHub Actions"。
- README 的中英文两部分在开头加上在线 demo 的链接。

## 7. 测试与检查

| 部分 | 怎么测 |
|---|---|
| 模拟数据 | 单元测试：同一时间点结果相同；读数对齐整分钟；离线房间的 `age_s` 超过离线阈值；各时间范围的点数和桶宽与服务端一致；不存在的房间返回 404 |
| 接口一致 | 类型检查：模拟数据的返回值按 `openapi.json` 生成的类型检查 |
| 演示模式 | 单元或构建检查：demo 构建里没有 service worker 注册、没有 web manifest |
| 端到端 | Playwright 打开构建好的网站：落地页显示，手机框里的 demo 列出四个房间、离线房间显示离线；全屏 demo 能进入房间并看到曲线；在房间页刷新仍然正常 |
| 一键检查 | `scripts/check.sh` 包含网站的构建和上述测试，CI 照旧跑这个脚本 |

## 8. 留给实现者决定

- 拦截 `/api/...` 请求的具体做法（例如在 demo 入口替换 `fetch`），只要不改现有页面和组件。
- 子路径下刷新不 404 的具体做法（例如 GitHub Pages 的 `404.html` 回退，或 demo 改用 hash 路由）。
- 落地页用 React 写还是用纯 HTML/CSS 写，以及具体的视觉样式；要和网页现有的配色和深浅色模式协调。
- 手机外框的实现方式（例如 `iframe` 嵌入全屏 demo 页）。
- 各房间的基准温湿度、起伏幅度和信号强度范围，只要看起来像真实的家。
